# UX-ARCH-03 — إصلاح استعادة جلسة Admin من المنصة الرئيسية

**التاريخ:** 05/11/2026  
**بلاغ ميداني:** حساب Admin يظهر مسجلاً دخوله في المنصة الرئيسية، لكن `/prototypes/ux-arch-03/admin/` يعرض «يجب تسجيل الدخول بحساب إدارة الموقع».

## السبب المؤكد
تستعمل المنصة الرئيسية معرّف Supabase Auth من الشكل `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` وتخزن الجلسة تحت مفتاح `official_report03_cloud_session_v1` في localStorage أو sessionStorage.

كان `validId` في `prototypes/ux-arch-03/admin/api.mjs` يستخدم تعبيرًا نظاميًا **بأربع مجموعات فقط** (`8-4-4-12`) بدل خمس مجموعات (`8-4-4-4-12`). لذلك رفض كل معرّف مستخدم صحيح، حتى لو كانت الجلسة المخزنة متاحة في اللسان.

## التصحيح
1. أصبح فحص UUID صحيحًا ذا خمس مجموعات.
2. يظهر «إدارة الموقع» للمسؤول فقط في قائمة المنصة الرئيسية؛ الانتقال في اللسان نفسه يتيح إعادة استخدام sessionStorage عند تعذر localStorage. لا تمرر الجلسة أو مفاتيحها عبر عنوان URL.
3. وفرت لوحة إدارة الموقع تسجيل الدخول المباشر بحساب Admin نفسه عن طريق Supabase Auth؛ لا تُنشأ حسابات جديدة ولا تُحفظ كلمة المرور.
4. إذا استعمل Admin مسار الدخول المباشر، تحفظ جلسته في `official_report03_admin_session_v1` ضمن sessionStorage فقط، بدل الكتابة فوق جلسة المفتش الموجودة في `official_report03_cloud_session_v1`.
5. يستمر التحقق الخادمي من `is_admin=true` و`approved=true` و`account_status='approved'`. ولا تكفي إظهار زر أو وجود جلسة لتحقيق صلاحية إدارية.
6. أُضيفت نسخ موارد (cache busting) حتى لا يستخدم Brave ملفات JavaScript القديمة.

## التحقق
اختبارات `tests/ux-arch-03-admin-signin-regression.test.mjs` تغطي الاستعادة من localStorage، والاستعادة في اللسان نفسه من sessionStorage، وتسجيل Admin المباشر دون استبدال جلسة المفتش، والرفض الآمن لكلمة مرور خاطئة، وانتقال إدارة الموقع في اللسان نفسه.

**نتيجة CI:** 574 اختبارًا ناجحًا، دون فشل، على الفرع.

**حدود التحقق:** هذه اختبارات برمجية تحاكي التخزين والمصادقة؛ يبقى تأكيد النجاح في Brave على جهاز المستعمل مطلوبًا. لا يتطلب الإصلاح ترحيل قاعدة بيانات ولا تغيير صلاحياتها.
