# M2.1 — الحسابات المهنية وسجل المؤسسات المركزي

الحالة: **شيفرة تحضيرية قيد التفعيل**. لا يصبح السجل المشترك عاملًا بمجرد نشر الملفات؛ يجب إنشاء مشروع Supabase وضبط الاتصال واعتماد أول حساب.

## ما أنجز
- واجهة اختيارية فوق المحرر الحالي: حساب مفتش، تحقق بالبريد الإلكتروني، واعتماد مسؤول بعد التحقق من الهوية المهنية.
- سجل مشترك للمؤسسات **ورؤسائها**. جميع المفتشين المعتمدين يستطيعون الإضافة والتعديل دون موافقة مسبقة.
- سجل تغيرات PostgreSQL ذري يبين **القيم السابقة والجديدة لكل حقل تغيّر** مع هوية المحرر والتاريخ.
- إشعارات داخل الموقع لكل مفتش معتمد آخر؛ تُحفظ حتى قراءتها، ويجري تحديثها دوريًا عند فتح لوحة الحسابات.
- تحقق من تعارض النسخ: تحديث المؤسسة مشروط برقم إصدارها، ويُرفض التحديث الأقدم دون إتلاف نص المستخدم.
- يمكن للمسؤول اعتماد الحسابات الجديدة دون أي أفضلية مهنية في صلاحيات تحرير المؤسسات.
- التقارير والمعاينات والتوصيات والفرق لا تزال في ذاكرة التبويب فقط ولا تُرسل إلى Supabase.
- يظل السجل المحلي كما في M1.9، ويمكن نقله عبر JSON. لا يوجد استيراد تلقائي إلى السجل المركزي.

## إعداد المشروع — مهمة مالك الموقع

1. افتح https://supabase.com/dashboard وأنشئ مشروعًا جديدًا. احفظ كلمة مرور قاعدة البيانات في مدير كلمات مرور خاص، ولا تضعها في GitHub.
2. من SQL Editor شغّل كامل ملف supabase/migrations/001_inspectors_institutions.sql. يجب انتهاء التنفيذ بنجاح.
3. من Authentication → URL Configuration اضبط:
   - Site URL: https://scientifica007.github.io/Official_report_template_03/
   - Redirect URLs: https://scientifica007.github.io/Official_report_template_03/
   - أبقِ خيار تأكيد البريد الإلكتروني مفعّلًا.
4. من Project Settings → API Keys انسخ Project URL ومفتاح Publishable (الذي يبدأ sb_publishable_)، أو مفتاح anon العام القديم. **لا تستخدم** service_role أو sb_secret_ في أي ملف على GitHub.
5. افتح cloud-config.js وضع رابط المشروع ومفتاح Publishable في supabaseUrl وpublishableKey. هذان القيمتان عامتان بطبيعتهما، والحماية الحقيقية بواسطة RLS.
6. بعد نشر الموقع، افتح «الحسابات والسجل المركزي» وسجل حسابك المهني. أكد عنوان البريد الإلكتروني من الرسالة.
7. ارجع إلى Supabase SQL Editor ونفذ الأمر التالي بعد استبدال YOUR_VERIFIED_EMAIL بالبريد المؤكد:

       UPDATE public.inspector_profiles
       SET approved = true, is_admin = true
       WHERE email = 'YOUR_VERIFIED_EMAIL';

   تأكد أنه تم تعديل **صف واحد**، لا صفرًا؛ ثم حدّث صفحة الموقع.
8. بعد ذلك يمكنك اعتماد بقية المفتشين من واجهة المسؤول.

## اختبارات القبول بعد الاتصال الحقيقي

- زائر أو حساب غير معتمد: لا يستطيع قراءة المؤسسات أو تاريخ تعديلها عبر API.
- حساب معتمد: يضيف مؤسسة جديدة يراها مفتش آخر من جهاز مختلف.
- تغيير اسم رئيس المؤسسة: يظهر للآخرين إشعار بالقديم والجديد وهوية المفتش والتاريخ.
- جهازان يفتحان سجلًا واحدًا ثم يحدث أحدهما البيانات: يجب منع حفظ نسخة الجهاز الآخر القديمة.
- محو تقرير من المتصفح لا يؤثر على سجل المؤسسات المشترك.
- التقرير الصادر سابقًا يبقى محتفظًا ببيانات المؤسسة كما كانت وقت إصداره.
- في حال تعطل Supabase يظل محرر التقرير المحلي والتصدير يعملان.

## الأمن وحدود هذه الشريحة

- إنشاء الحساب لا يعني اعتماد المفتش، ولا يمكن لحساب عادي اعتماد نفسه.
- جميع الجداول مشترطة بـ RLS، وسجل التعديلات يكتب حصريًا من مشغلات قاعدة البيانات.
- لا يُسمح للواجهة بحذف المؤسسات المركزية، ولا بكتابة سجل تعديلات غير حقيقي.
- جلسة الحساب في sessionStorage للتبويب فقط، ولا تخزن بيانات التقارير في السحابة.
- التنبيهات محفوظة في قاعدة البيانات، لكنها تظهر عند استخدام الموقع مع اتصال إنترنت.
- **التعاون اللحظي وتوزيع المجالات والاقتراحات المتبادلة والتوقيع المشترك للتقارير ليست جزءًا من M2.1**، وتأتي في M2.2.

## نقل المؤسسات المحلية مستقبلًا

سجل M1.9 المحلي يبقى على الجهاز. قبل استيراده مركزيًا ينبغي فحص رمز كل مؤسسة وتعارض بيانات رئيسها، وحفظ ملف JSON احتياطي، وطلب تأكيد المستخدم على كل تعارض. لا تُنقل المؤسسات القديمة تلقائيًا ولا تُرسل المعاينات ضمن سجلها.
