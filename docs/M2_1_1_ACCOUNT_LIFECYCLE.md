# M2.1.1 — إدارة دورة حياة حسابات المفتشين

## الوظائف

توجد أربع حالات: **قيد الانتظار** (pending)، **معتمد** (approved)، **مرفوض** (rejected)، **معلّق** (suspended).

يستطيع المسؤول اعتماد طلب جديد بعد تأكيد البريد، ورفضه، وتعليق حساب معتمد، وإعادة تفعيل حساب معلّق أو اعتماد حساب مرفوض سابقًا. يمكن إدخال سبب للقرار (اختياري، حتى 1000 حرف). يسجل النظام صاحب القرار والمفتش المعني والحالة السابقة والجديدة والتاريخ والسبب.

لا تتغير حالة الحسابات المعتمدة أو المعلقة سابقًا أثناء تطبيق الترحيل؛ الحسابات ذات approved=true تبقى approved، وذات approved=false تنتقل إلى pending (لأن «مرفوض» لم يكن موجودًا من قبل).

يُمنع المسؤول من تغيير حالة حسابه الشخصي، ومن تعليق أي حساب إداري عبر واجهة إدارة الحسابات. صلاحيات المفتشين المعتمدين في تعديل المؤسسات متساوية.

## ترتيب التفعيل الآمن

**لا تدمج طلب GitHub قبل نجاح الترحيل في Supabase، لأن الواجهة الجديدة تحتاج إلى عمود وجدول ودالة جديدة.**

1. افتح Supabase → المشروع uxtsyzyotnohxvopgcmh → SQL Editor → New query.
2. انسخ الملف كاملًا من supabase/migrations/002_inspector_account_lifecycle.sql.
3. نفذ SQL مرة واحدة؛ يجب أن تنتهي العملية دون أخطاء. لا تعاود التشغيل في حال خطأ قبل مراجعته.
4. استعلم عن الحسابات لمراجعة الوضع الحالي:

```sql
select account_status,approved,is_admin,count(*)
from public.inspector_profiles
group by 1,2,3 order by 1,2,3;
```

5. تأكد أن الحساب الإداري القائم account_status=approved وapproved=true وis_admin=true، وأن الحساب الثاني التجريبي ما زال pending.
6. تأكد أن جدول inspector_account_decisions موجود وRLS مفعّل.
7. بعد تأكيد النجاح، ادمج طلب GitHub المخصص لـ M2.1.1، وانتظر نجاح النشر، ثم حدث الموقع (Ctrl+Shift+R).

## الأمن

يظل الحقل approved القديم متزامنًا ذريًا مع account_status، لذلك تعمل سياسات RLS السابقة دون تغيير. يُسمح فقط لمسؤول معتمد باستدعاء دالة set_inspector_account_status، وهي تتحقق من تأكيد البريد ومن انتقال الحالة ومن منع القرار بشأن الحساب الشخصي، وتقفل سجل المستهدف لمنع تعارض القرارات.

يسجل جدول inspector_account_decisions القرارات تلقائيًا من دالة قاعدة البيانات، ولا يسمح للعميل بكتابة السجل أو حذفه. يستطيع المسؤول قراءة جميع القرارات وصاحب الحساب قراءة ما يخص حسابه فقط.

دالة approve_inspector القديمة تظل متاحة للنسخ المخبأة مؤقتًا، لكنها تمر عبر نظام التدقيق الجديد ولا يمكن استعمالها لسحب الاعتماد.

## اختبار القبول

1. ارفض حسابًا تجريبيًا قيد الانتظار، وتحقق من انتقاله إلى قائمة المرفوضين.
2. اعتمد الحساب نفسه بعد الرفض، وتحقق من استعادة إمكان تسجيل الدخول إلى السجل المشترك.
3. علّق حسابًا معتمدًا غير إداري، وتحقق من توقف وصوله حتى لو كان متصلًا.
4. أعد تفعيله، وتحقق من عودة وصوله.
5. راجع سجل القرارات وتأكد من ظهور الاسم والقرار والوقت والسبب عند إدخاله.
6. تحقق من بقاء الحساب الإداري الأول معتمدًا، وعدم تغير سياسة حفظ التقارير أو التصدير.

**المهم:** نشر شيفرة GitHub لا ينفذ تعليمات SQL على مشروع Supabase تلقائيًا.
