# UX-ARCH-03 — إدارة مستقلة عن التفتيش، حرية المقاطعات والمؤسسات المشتركة

**تاريخ تحديث التصميم:** 05/11/2026

**الحالة (05/11/2026):** طُبقت هجرة UX-ARCH-03 بنجاح على **QA ثم الإنتاج** بعد إصلاح المحددات النصية SQL. اجتاز الفرع 567 اختبارًا آليًا، إضافة إلى اختبار صلاحيات مباشر داخل معاملة QA أُلغيت بعد الاختبار. واجهة Admin والانتقال التلقائي من UX-ARCH-02 متاحان في الفرع، بانتظار دمجهما ونشرهما على GitHub Pages. لا تُغيَّر مؤسسات أو مقاطعات الإنتاج تلقائيًا.

## 1. قواعد التصميم المعتمدة

1. **حساب Admin** شخصي لصاحب الموقع ويُستخدم لتسيير الموقع وإدارته وصيانته، ولا يحتاج إلى مقاطعة عمل ولا يُعرض ضمن المفتشين.
2. **حساب المفتش** منفصل ويستخدم للتحضير والتفتيش والتقارير وتخزين بياناته الخاصة، ومقاطعة العمل تحدد نطاق الاطلاع المهني المعتاد.
3. يحدد `Admin` **اسم المقاطعة ورمزها بحرية**، بما فيه `12` و`12-01` و`12-أ`. يشترط وجود قيمة غير فارغة وفريدة دون محارف تحكم، ولا توجد قاعدة تربط الرمز بولاية السكن أو رمز الولاية.
4. يمكن إعادة تسمية مقاطعة أو تغيير رمزها **مع بقاء UUID الداخلي ثابتًا**، وبقاء المفتشين والبيانات المرتبطة بها دون تغيير.
5. **المؤسسة سجل واحد** متعدد المقاطعات: يمكن أن يُتاح لمقاطعة أو عشر، دون نسخ السجل أو فرض مطابقة الولاية.
6. يستطيع `Admin` **إنشاء مؤسسة دون نشرها لأي مقاطعة بعد**، ثم توزيعها أو سحب إتاحتها للمقاطعات، دون حذف السجل المركزي.
7. يستطيع `Admin` ربط مؤسسة موجودة بالسجل القديم بالمؤسسات الجديدة **باختيار صريح**؛ يحفظ رابط `legacy_institution_id` فريدًا، ولا يحذف أو يعيد كتابة المؤسسة الأصلية.
8. يستطيع المفتش اقتراح مؤسسة للنشر؛ يدير `Admin` قبول الطلب أو رفضه عبر جميع المقاطعات. السبب اختياري، وتُسجل هوية المسؤول ووقت القرار.
9. يحتفظ `Admin` بحق قراءة **سجلاته الشخصية القديمة فقط** إن كانت محفوظة قبل فصل الأدوار، ولا يحصل على اطلاع تلقائي على سجلات المفتشين الشخصية.
10. تمنح سياسات RLS للمفتش رؤية المؤسسات المنشورة **المرتبطة بمقاطعة عمله** فقط في السجل الجديد، وتحتفظ المؤسسات ببياناتها الأصلية في قاعدة البيانات.
11. لا يُغيَّر دليل المفتشين القديم أو سياسات `shared_institutions` الشاملة ضمن هذا الترحيل؛ فصلها النهائي يحتاج ترحيلًا آخر مضبوطًا.

## 3. ضمانات بيانات الإنتاج

في بداية العمل كانت المقاطعتان المحفوظتان بالفعل: `09-00` (البليدة)، `12-00` (تبسة). **لا تُنشأ مقاطعة 12 تلقائيًا** بدل 12-00؛ يستطيع Admin تعديل رمز المقاطعة الموجودة دون تغيير معرفها الداخلي.

التجارب السابقة في الإنتاج أنشأت تحضيرًا محفوظًا وسجلًا خاصًا وطلب نشر. لا يُعدّل الترحيل المقترح محتواها أو يوزعها تلقائيًا.

**الأهم:** قاعدة المؤسسات القديمة ليس لها تقسيم صحيح موثق حسب مقاطعة العمل. لا يُجري هذا التغيير إعادة تصنيف أو نشرًا جماعيًا لها. على Admin اختيار توزيع المؤسسات من الواجهة بعد اختبارها.

## 4. نتائج الاختبار الحالية وحدودها

- فُحصت صياغة ملفات JavaScript الثلاثة عبر مترجم JavaScript في وضع التحليل، دون تشغيل عمليات الشبكة.
- اجتازت قواعد ومعطيات الواجهة **15 اختبارًا محليًا**؛ منها إنشاء رمز عربي مركب، وجود مؤسسة واحدة في مقاطعتين، تأجيل التوزيع، منع إظهار صاحب حساب Admin ضمن قائمة المفتشين، والإبقاء على روابط المعرّف عند إعادة التسمية.
- **نجحت اختبارات GitHub Actions الكاملة: 567/567 دون فشل** للنسخة التي تحتوي على الإصلاحات والتوجيه إلى لوحة Admin.
- **طُبقت هجرة SQL بالفعل على QA والإنتاج.** نجحت اختبارات عملية باستعمال سياقَي مستخدمين داخل قاعدة QA في معاملة واحدة منتهية بـ`ROLLBACK`: فُصل حساب Admin عن المفتش؛ أنشأ Admin رمزي `12` و`12-أ`؛ تغيّر `12` إلى `12-01` دون تغير هوية السجل؛ أنشئت مؤسسة غير موزعة ثم أُتيح السجل نفسه لمقاطعتين؛ رفض الخادم محاولة المفتش تعديل مقاطعة؛ وعند إزالة إسناد المؤسسة من مقاطعته لم تعد ظاهرة له. هذه اختبارات RLS/RPC خادمية، ويظل اختبار حسابين فعليين عبر REST والمتصفح شرطًا للاعتماد الميداني النهائي.

## 5. خطة الاختبارات الحية المطلوبة قبل الدمج

1. أخذ لقطة إحصائية قبل وبعد الترحيل في QA، والتحقق من بقاء المهام والأعضاء والمؤسسات.
2. تجربة Admin ينشئ مقاطعة `12`، ثم `12-أ`، وتعديل اسم `12` ورمزها إلى `12-01` دون المساس بمعرفها الداخلي أو انتماء المفتشين.
3. تجربة Admin دون مقاطعة عمل؛ يجب السماح له بإدارة الموقع ورفض دخوله كحساب مفتش مهني.
4. تجربة إنشاء مؤسسة **دون أي مقاطعة**، ثم اختيار مقاطعتين لنفس المعرف، ثم سحب الإتاحة من إحداهما؛ تتغير نتائج القراءة حسب حساب المفتش ومقاطعته فقط.
5. تجربة ربط مؤسسة قديمة ثم محاولة إعادة ربط **نفس السجل**؛ يجب منع التكرار وحفظ الأصل.
6. تجربة تقديم مفتش طلب نشر واعتماده من حساب Admin دون اشتراط تطابق مقاطعة مسؤول الموقع مع أي مقاطعة.
7. اختبارات API/REST/RLS بهويتين مختلفتين: مفتش ينتمي إلى مقاطعة أ لا يرى بيانات مقاطعة ب غير المنشورة له، ولا يقرأ سجلاتها الخاصة، ولا يستطيع تنفيذ إجراءات Admin حتى بمعرف مورد معروف.
8. اختبار واجهات الترسم والتفتيش المعمق وPDF/DOCX/JSON قبل أي دمج ونشر.

**قرار النشر:** بعد نجاح QA وتطبيق الإنتاج وفحص أعداد السجلات واختبارات CI، يجوز دمج واجهة Admin المستقلة إلى `main` ونشرها مع إبقاء صفحة التقارير والمهمات القديمة دون تغيير. **الفصل الشامل لدليل المفتشين والمؤسسات التاريخية ما زال مشروعًا لاحقًا**، لأن سياسات `inspector_profiles` و`shared_institutions` القديمة لم تُستبدل ضمن هذا الترحيل.
