# M5.0 — دمج نموذج الترسيم في بوابة النماذج، وتصميم حسابات اللجنة المؤقتة

**التاريخ:** 02/11/2026
**قرار المستخدم:** قُبل الإملاء الصوتي عمليًا على Edge للحاسوب وعلى Chrome/Brave للهاتف، مع القيود المعروفة في Brave للحاسوب وFirefox للهاتف. النموذج الأول وتصديراته PDF/DOCX/JSON مقبولة. يجب عدم تغيير مسار طباعتها.

## المرحلة المنفّذة الآن — دمج التنقل دون خلط البيانات

- أصبحت «نماذج التفتيش» تبويبًا في لوحة قيادة المفتش المعتمد، تعرض محرر النموذج الرسمي 03، ومختبر الترسيم الميداني المقبول، ونموذجًا شخصيًا ثانيًا مؤجلًا.
- يسمح رابط الترسيم بفتح المحرر الموجود كما هو في تبويب مستقل؛ توجد وصلة عودة للمنصة.
- **التكامل الحالي ملاحي فقط.** مختبر الترسيم لا يستعمل حتى الآن جلسة المفتش ولا الحفظ السحابي ولا دعوة أعضاء اللجنة. الرابط العام على GitHub Pages ليس نظام مصادقة، ولا يجوز تقديمه على أنه محمي أو أن إسناده يمنح صاحبه هوية معتمدة.
- لا تغيير في مولدات وثائق الترسيم `preview.mjs`, `docx-export.mjs`, `document-export-contract.mjs`، ولا شبكة العلامات أو موافقات اللجنة أو موضع التذييل. كذلك لم تتغير RLS وقواعد تخزين مهام النموذج 03.

## المتطلب المقبول — حسابات أعضاء لجنة مؤقتة

### نموذج الملكية والأدوار

1. للمفتش رئيس اللجنة حسابه المهني المعتمد، وهو مالك *مهمة الترسيم* ومشرف إدارة وصول أعضائها؛ هذه الصلاحية محصورة بسياق لجنة الترسيم ولا تمس تساوي المفتشين الزملاء في مهام التفتيش المعمق 03.
2. تُنشأ **ثلاثة مقاعد مستقلة**: العضو الأول، العضو الثاني، العضو الثالث. يمكن لكل مقعد الحصول على **حساب مؤقت مستقل**؛ دون افتراض أن كل عضو مفتش أو يحتاج إلى حساب مهني دائم.
3. للمقعد اسم عرض، ورمز مستخدم فريد، وكلمة مرور قوية **تُعرض عند الإنشاء مرة واحدة**، ورابط للمهمة والمقعد فقط. الرابط لا يحتوي كلمة المرور أو رمز جلسة ولا يمنح حق الوصول دون إدخال بيانات الدخول.
4. يمنح الحساب الوصول إلى **مهمة واحدة ومقعد واحد**. لا يسمح بمطالعة ملفات النموذج 03 أو مؤسسات المفتش أو بيانات بقية الأعضاء أو تعديل تقديراتهم أو درجاتهم.
5. يمكن للعضو إدخال علاماته وتقديراته وإرسال مساهمته بعد مراجعتها. يتعطل تحريرها بعد الإرسال، حتى إعادة الفتح بأمر مخول؛ لا يؤدي ذلك إلى مسح سجل الإرسال الأصلي.
6. تبقى مساهمات الأعضاء مستقلة عن **الخلاصة النهائية** التي يراجعها المفتش ويحررها؛ لا تتغير العلامات النهائية تلقائيًا بمجرّد ورود مساهمة.
7. المدة محدودة وقابلة للتقليص؛ إغلاق المهمة أو إلغاء أحد الحسابات يسحب الوصول فورًا على مستوى صلاحيات قاعدة البيانات، حتى إذا بقي لدى العضو رمز جلسة JWT صالح لبعض الوقت.
8. يختار المفتش بعد إنجاز المداولة والطباعة: **«إلغاء الوصول»** أو **«إزالة حساب العضو المؤقت»** بعد تنبيه واضح. تُحفظ مساهماته في سجل المهمة مع المعرّف التاريخي واسم الدور، **ولا تمحى ضمنيًا مع الحساب**. أي محو نهائي للبيانات إجراء مستقل صريح، ويحتاج إلى سياسة احتفاظ واضحة.
9. يمكن إعادة إصدار بيانات دخول عضو واحد دون مساس بالحسابات الأخرى أو الوثائق المصدّرة.
10. لا تصبح الطباعة اعتمادًا إلكترونيًا، ولا يتحول إنشاء الحساب المؤقت إلى سلطة إدارية على اللجنة خارج المهمة.

### التصميم الأمني الإلزامي (لم يُنشر على الخادم بعد)

- **لا تخزين لكلمات المرور في JSON أو في localStorage أو في رابط أو في GitHub أو في جدول عام.**
- إنشاء الحساب وتغييره وحذفه عبر **Supabase Auth Admin API على جهة الخادم فقط** (Edge Function ذات صلاحيات خدمة محفوظة في الأسرار)، لا من JavaScript المنشور على GitHub Pages.
- لا يكفي تعيين اسم المستخدم وكلمة المرور في واجهة HTML. يجب التحقق من المفتش المالك في الخادم باستخدام جلسة معتمدة وقيود قاعدة البيانات، مع قاعدة RLS مستقلة للمهام المؤقتة، وقاعدة دور/مقعد/انتهاء صلاحية لكل عملية قراءة وكتابة.
- يمكن استعمال معرف دخول اصطناعي داخلي لتغليف اسم المستخدم عند الحاجة إلى بريد Supabase Auth، مع إدارة العنوان والحساب في الخادم، ودون انتحال بريد إلكتروني حقيقي أو إرسال رسائل إلى عنوان مزيف. تصميم طريقة التعريف النهائية يحتاج إلى تجربة Supabase قبل التفعيل.
- لا تعتمد صلاحيات القراءة والكتابة على `user_metadata` الذي يستطيع المستخدم تغييره، ولا على تحقق DOM فقط. تُفحص حالة المهمة والمقعد ووقت انتهاء الصلاحية في كل طلب ذي امتياز.
- حذف `auth.users` لا يزيل صلاحية JWT صادر سلفًا لحظيًا دون تحقق إضافي؛ ينبغي أن توقف سياسات RLS الوصول فور تفعيل `revoked_at` أو إغلاق المهمة، ويُبطل التجديد بحذف الحساب السحابي. عدم استخدام روابط تتحول إلى مفاتيح دخول.
- تسجيل محاولات غير ناجحة وفرض حدود معدّل، وإمكانية إعادة تعيين كلمة المرور وإلغاء جميع الجلسات؛ عدم إرسال كلمة المرور عبر سجل أحداث أو رسالة عامة.
- فصل بيانات المهمة والمساهمات في جداول جديدة، مع حماية عدم الحذف الارتجاعي للتقديرات الأصلية، وRLS اختبارات سماح ومنع تشمل: عضو آخر، عضو انتهت صلاحيته، مفتش آخر، زائر غير معتمد، حساب مغلق، مستخدم مُلغى.
- لا تطبق أي ترحيل أو وظيفة صالحة لإنشاء المستخدمين في مشروع Supabase الإنتاجي قبل اجتياز اختبار قاعدة بيانات مستقل وتفويض المالك؛ ولا تضع `service_role` في الملفات العامة.

### تسلسل التنفيذ بعد دمج التنقل

1. جداول «مهمة الترسيم»، «مقعد اللجنة»، «مساهمة العضو»، «سجل إجراءات حساب العضو» مع RLS وتعريف حالات الانتقال.
2. وظيفة خادمية لإنشاء حساب عضو مؤقت بكلمة سر قوية وإرجاعها مرة واحدة، وإلغاء الوصول/إزالة الحساب، مع إذن محدد للمفتش المالك.
3. صفحة دخول مستقلة للأعضاء (الرابط + اسم المستخدم + كلمة المرور)، ومحرر مساهمة العضو المعين فقط مع الإملاء الصوتي.
4. شاشة رئيس اللجنة لدعوة الأعضاء، وإعادة إصدار كلمة المرور، ومتابعة الإرسال، واستيراد مساهمات الأعضاء في النموذج الأول دون تغيير مخرجاته.
5. اختبار عملي بثلاثة حسابات على أجهزة مختلفة، إغلاق/إلغاء صلاحية الحساب أثناء جلسة مفتوحة، حفظ المساهمات بعد إزالة الحساب، وأخيرًا فحص PDF/DOCX/JSON من جديد.

**حالة التسليم:** دمج النماذج في لوحة القيادة متاح، وحسابات أعضاء اللجنة الموقتة **متطلب موثق ولم تُفعّل بعد**. لا يجوز عرض أي بيانات دخول مؤقتة مزعومة قبل نشر الخادم واختبار RLS.
